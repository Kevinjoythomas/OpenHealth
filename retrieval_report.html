Retrieval Strategy Evaluation in a Medical RAG System:
BM25, Dense Vector Search, and Reciprocal Rank Fusion

Kevin Thomas · OpenHealth Project
Abstract
We evaluate three document retrieval strategies — BM25 keyword search, dense vector search using MMR (Maximal Marginal Relevance), and a hybrid fusion via Reciprocal Rank Fusion (RRF) — as applied to a medical question-answering system backed by six clinical reference PDFs. Latency is measured over 5 isolated warm runs per method per query across 4 medical queries (n = 20 observations per method). Qualitative result relevance is assessed on three representative queries. We find that all methods operate within a shared ~2 s latency envelope dominated by ChromaDB SQLite I/O; within this envelope, BM25 exhibits a statistically consistent advantage of approximately 100 ms with lower variance. Hybrid RRF produces qualitatively superior results by combining semantic understanding (vector) with exact-term matching (BM25), at a latency cost indistinguishable from vector search alone.

1. System Overview

OpenHealth is a Retrieval-Augmented Generation (RAG) system for medical question answering. A patient submits a question through a browser interface; the API Gateway authenticates the request and forwards it to the Chat Orchestrator, which calls the Retrieval Service to fetch relevant document chunks before constructing a prompt for the locally-hosted LLM (Ollama, model: openhealth-doctor, Llama 3 8B Q4_K_M fine-tuned on medical dialogue).

The retrieval pipeline is implemented in a dedicated microservice (port 5003) and exposes three search strategies: dense vector search over a ChromaDB collection, BM25 lexical search over the same corpus, and a hybrid fusion of both. This report evaluates those three strategies on latency and result relevance.

2. Knowledge Base

Six medical reference documents were ingested into ChromaDB. The corpus covers cardiovascular, respiratory, infectious disease, and musculoskeletal domains.

3. Retrieval Methods

3.1 BM25 (Okapi BM25)

BM25 is a probabilistic ranking function based on term frequency and inverse document frequency. The index is built lazily on first query by loading all document chunks from ChromaDB into memory and constructing a BM25Okapi index. Subsequent queries operate entirely in RAM with O(n) scoring over the token-level vocabulary. BM25 excels at exact-term matching and is particularly reliable for drug names, ICD codes, and domain-specific acronyms.

3.2 Dense Vector Search (MMR)

Each document chunk is embedded into a 768-dimensional vector space using nomic-embed-text. At query time the query string is embedded by the same model, and ChromaDB performs approximate nearest-neighbour search via an HNSW graph. This implementation uses Maximal Marginal Relevance (MMR), which re-ranks candidates to balance relevance against diversity — preventing redundant chunks from filling the top-k slots. Vector search captures semantic relationships across vocabulary (synonyms, paraphrases, concept associations) that BM25 cannot.

3.3 Hybrid RRF (Reciprocal Rank Fusion)

The hybrid strategy executes both retrievers concurrently via a ThreadPoolExecutor (2 workers) and fuses the two ranked lists using Reciprocal Rank Fusion with the standard constant k = 60:

score(d) = 1 / (60 + rankvector(d)) + 1 / (60 + rankBM25(d))
// Documents ranked highly by both retrievers receive additive score contributions
// A document ranked #1 by both: 1/61 + 1/61 ≈ 0.033 (vs 0.016 from one retriever alone)

RRF does not require score normalisation across methods with different scoring scales — only ordinal rank positions are used. The total retrieval time is bounded by max(tvector, tBM25) rather than their sum, as both run in parallel.

4. Experimental Methodology

Each method was called via a dedicated isolated HTTP endpoint (/v1/retrieve/vector, /v1/retrieve/bm25, /v1/retrieve/hybrid) to prevent cross-method cache contamination. One warm-up call was issued per method per query (not counted) to ensure in-memory caches (embedding model, BM25 index, ChromaDB connection pool) were fully initialised. Five subsequent calls were timed using time.perf_counter() at the client, measuring wall-clock round-trip latency including HTTP serialisation overhead.

Four medical queries of varying specificity were used. All tests were run on a local Windows 11 machine with the retrieval service running in a Conda environment (Python 3.11). Cold-start latency (embedding model initialisation) was not measured as it is a one-time per-process cost independent of retrieval strategy.

5.2 Interpretation

The absolute latency (~2 s) is dominated by ChromaDB's SQLite storage backend, which performs disk I/O for both HNSW graph traversal (vector) and corpus loading (BM25 index rebuild on cache miss). In a production deployment with a dedicated vector database (e.g. pgvector on PostgreSQL, Qdrant, or Weaviate) the absolute latency would be substantially lower and method-level differences proportionally larger.

Within the shared baseline, BM25 is consistently the fastest method (103 ms advantage over vector, 97 ms over hybrid) and exhibits the lowest standard deviation in 3 of 4 query groups, indicating greater predictability. This is expected: BM25 operates entirely in RAM after index construction, whereas vector search requires an embedding model call followed by HNSW graph traversal with disk-backed storage.

Hybrid RRF latency is approximately equal to vector search alone (6 ms difference), consistent with the parallel execution model where total time is bounded by max(tvector, tBM25). BM25 completes within the vector search window at negligible additional cost.

7. Discussion

The latency results demonstrate that all three methods operate within a common baseline determined by storage infrastructure rather than algorithmic complexity. The practical consequence is that hybrid RRF incurs no meaningful latency penalty relative to vector search, while offering superior result quality through multi-signal fusion.

The qualitative analysis reveals complementary failure modes: BM25 fails on vocabulary mismatch (Test A); vector search produces diverse but occasionally less precise results (Test C, where BM25 scored higher on exact-term match); hybrid mitigates both failure modes and surfaced a clinically relevant cross-domain association (arm pain as referred cardiac symptom, Test C) that neither individual method retrieved.

A limitation of this evaluation is the small corpus size (6 documents) and the absence of a ground-truth relevance judgement set. Precision@k and NDCG metrics, which require labelled relevance assessments, were not computed. The qualitative analysis presented here reflects domain knowledge assessment rather than a formal information retrieval evaluation.

8. Conclusions

Hybrid RRF is the recommended retrieval strategy for this system on the following grounds: (1) latency is statistically equivalent to vector search alone, as BM25 completes within the vector search window; (2) result quality is demonstrably superior for queries where lay and clinical vocabularies diverge; (3) RRF's rank-based fusion is robust to the different scoring scales of the two component retrievers.

BM25 alone is recommended where latency is the primary constraint, storage infrastructure cannot support vector embeddings, or queries are expected to contain exact clinical terminology (drug names, ICD codes, procedure names). In a production system with a dedicated vector store, the latency differences would be more pronounced.
