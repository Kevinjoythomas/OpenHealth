Fine-tuned Medical Model

LoRA fine-tuned Llama 3 8B (rank=8, alpha=16, 20.97M trainable params — 0.26% of total) on 112K real patient-doctor consultations. Trained via Unsloth for efficiency. Training loss: 3.74 → 2.19 over 1,000 steps. GGUF Q4_K_M quantized and served via Ollama.

Hybrid Retrieval

BM25 and ChromaDB vector search run concurrently via ThreadPoolExecutor, fused via Reciprocal Rank Fusion. Latency matches vector-only (parallel, not sequential).

dns

Microservices

4 Flask services — API Gateway, Auth, Chat Orchestrator, and Retrieval — each independently deployable. SQLite + fakeredis in dev, Postgres + Redis in production.

The Response Pipeline

01

User Query

Natural language symptoms sent to API Gateway. JWT validated, rate limited, forwarded to Chat Orchestrator.

02

Hybrid Search

Retrieval Service runs BM25 + ChromaDB in parallel. Top-5 docs fused with RRF scoring.

03

Context Injection

Only docs above relevance threshold (RRF ≥ 0.020) are injected. Low-confidence sources filtered out.

04

LLM Response

Fine-tuned Llama 3 8B generates clinical guidance via Ollama. Sources cited when retrieval is confident.

Infrastructure Design

API Gateway (:5000) → Auth (:5001) · Chat Orchestrator (:5002) → Retrieval (:5003) → BM25 + ChromaDB + RRF → Ollama GGUF. Static frontend on Vercel, backend tunnelled via ngrok. Ingestion worker via Celery + RabbitMQ.

REST API · Open Source

Designed for Extensibility

OpenHealth exposes a clean REST API across 4 services. Swap Ollama for any model backend, ChromaDB for any vector store, or BM25 for any keyword retriever with minimal config changes. Runs locally without Docker — SQLite and fakeredis substitute automatically in dev mode.
